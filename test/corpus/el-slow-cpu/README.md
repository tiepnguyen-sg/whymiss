# el-slow-cpu

The execution client's CPU is capped to 8% of one core (cgroup v2 cpu.max) for the full duty window while spamoor keeps ~300 transactions per block flowing, so newPayload has real work to be starved of. The watched attester is on the same node and avoid_proposer_validators forces the block to arrive over gossip, so this node must actually import and validate it rather than having produced it. An unfaulted Prysm baseline separates local processing delay from a network-wide late block.
This is the first scenario that can exercise R-300 at all. That rule needs a rolling el_engine_calls_p99_ms baseline, which is a domain.MetricSample, and a corpus record used to carry only observations — so local.el_slow was unreproducible by construction, at any fault severity and under any load. Two things changed: records can now carry an optional samples.jsonl (timeline.LoadSamples), and faultinjector spends an epoch sampling Engine counters before choosing a duty so it has a real baseline to write (collectEngineBaseline). Expect roughly 6.4 minutes of extra wall clock per run, which is what 32 slots of history costs.
Why 8%. Engine work measured 361ms per block under spamoor load on an unthrottled node (beacon_block_delay_execution_time; it is 3-5ms on an empty chain, which is why every earlier attempt at this cause on an unloaded devnet was doomed regardless of the cap). R-300 needs the slot's Engine total to exceed thresholds.engine_spike_multiplier — 3.0 by default — times that baseline, and it needs validation to be the dominant stage with head_updated past the +4s deadline. An 8% quota is roughly a 12x slowdown, which clears both with margin. The neighbouring cl-slow-cpu recipes use 7-9% against the consensus client for the same reason.
