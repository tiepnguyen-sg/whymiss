# proposer-missed-concurrent-vc-pause

Originally set up to test `local.vc_disconnected` (Prysm's validator client
container frozen for the duty window, avoiding a same-node proposer conflict).
The real result was more interesting than intended: validator 23 (Lighthouse
range, unrelated to the paused node) held the proposer duty for this slot and
never produced a canonical block — confirmed by direct query well after the
slot passed (persistent 404).

## What was broken

Fault: pause applied to vc-2-geth-prysm for 20s, around slot 494.

## Recorded outcome

- Block observed for the duty slot: false
- Attestation published (seen in the pool): false
- Attestation included: false

## Why this is labelled `network.proposer_missed`, not `local.vc_disconnected`

Per `docs/causes.md`'s rule ordering, R-100 (proposer absent) fires before
R-400 (VC reachability) specifically because an absent block exonerates every
attester regardless of their own client health — with no block at all, there
was nothing for validator 33 to attest to, so its own paused VC cannot be
distinguished as *the* cause from these observations alone.

Kept and relabeled rather than discarded: a corpus scenario records what
actually happened, not what was expected to happen.
