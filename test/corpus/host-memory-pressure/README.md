# host-memory-pressure

The Lighthouse-paired execution client's cgroup v2 memory.high is capped to 128MB for the full duty window — well under geth's normal working set for this devnet, forcing sustained reclaim. memory.high throttles and reclaims rather than OOM-killing the process (unlike memory.max), which is what docs/causes.md's local.host.memory_pressure rule measures via PSI.


## What was broken

Fault: cgroup_mem applied to el-1-geth-lighthouse for 25s, around slot 2001.

## Recorded outcome

- Block observed for the duty slot: false
- Attestation published (seen in the pool): true
- Attestation included: false

## Measurement caveat

"Block observed: false" does not mean slot 2001 has no block — it does,
confirmed canonical via a direct query minutes after the fault reverted.
PollBlockSeen genuinely received HTTP 404 from cl-1-lighthouse-geth for
slot 2001 throughout the entire 36-second watch window: under this severe
a memory cap, el-1-geth-lighthouse could not validate the payload fast
enough for its paired CL to import the block within that window at all.
The attestation_published observation at 4.21s is consistent with this —
a validator client attests to whatever head it currently has at the
deadline, not necessarily the current slot's own block, so publishing
succeeded against a stale head while this slot's own block was still
unimported. Because BlockFound was false, CheckInclusion never ran, so
whether this validator's attestation was ultimately counted is unknown,
not confirmed absent.
