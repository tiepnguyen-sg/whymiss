# p2p-degraded-lighthouse

200ms of added latency (tc netem) on the Lighthouse consensus client's network path for the full duty window, simulating degraded peering / propagation.


## What was broken

Fault: netem applied to cl-1-lighthouse-geth for 20s, around slot 58.

## Recorded outcome

- Block observed for the duty slot: true — but ~18.2s into the slot,
  far more than the injected 200ms alone would explain.
- Attestation published (seen in the pool): true
- Attestation included: true, inclusion delay 1 (the best possible)

## A measurement caveat, honestly noted

The 200ms netem delay was attached to cl-1-lighthouse-geth's host-side veth —
every packet in or out of that container, not just P2P gossip. That includes
this tool's own HTTP polling of the same node's beacon API, which shares the
same delayed link. The ~18s gap between slot start and block_seen is real
(nothing here is fabricated) but is not a clean measurement of propagation
delay alone: it plausibly reflects the fault compounding with the tool's own
poll-and-retry behavior against a degraded connection, not 200ms of gossip
delay by itself. A future collector using the SSE event stream from a
*different*, undelayed vantage point would measure this more cleanly.
