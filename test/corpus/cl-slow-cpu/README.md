# cl-slow-cpu

The Prysm consensus client's CPU is capped to 5% of one core (cgroup v2 cpu.max) for the full duty window, while its paired execution client runs unthrottled — isolating CL-side validation slowness from EL-side slowness, which local.cl_slow's rule requires (Engine API duration under half of the validation stage).

## Measurement caveat

This tool polls cl-2-prysm-geth's own beacon API to detect block_seen —
the same container the fault throttles. A CPU-starved node may be slow to
serve its own HTTP API, not just slow to validate, so `block_seen`'s ~1.4s
offset (elevated vs. the ~0.6-0.7s baseline seen in unfaulted scenarios)
may partly reflect polling latency rather than pure validation delay. The
`inclusion_delay: 2` figure is not affected by this: it is read after the
fault has been reverted, once the node is no longer throttled.
