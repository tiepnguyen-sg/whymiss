# Case study: the May 2023 mainnet finality incidents

**What this shows.** A publicly documented incident whose root-cause chain begins
with a link whymiss names automatically, reproduced as a real fault on a real
devnet, with whymiss's unedited output.

**What this does not show.** whymiss did not diagnose the 2023 incident and could
not have. It is a single-node tool: it explains the duties of the validators it
watches, and says nothing about the network-wide client bug that made the
incident an incident. The claim here is narrower and checkable — the *first* link
in the published chain is one whymiss reports, with evidence, within one slot.

---

## The incident

On 11 and 12 May 2023 Ethereum mainnet lost finality twice inside 24 hours.
Participation fell to roughly **75%** at epoch 411,448, under nine points from
the two-thirds supermajority finality needs. The first episode lasted about two
epochs, the second about eight.

The published root cause is a chain, not a single fault:

1. An execution client stops responding, or responds too slowly.
2. Its consensus client keeps attesting — standard behaviour — but votes for an
   **old beacon block**, because it has no fresh head to vote for.
3. Those attestations are valid, but validating them requires a beacon-state
   regeneration.
4. Prysm's cache for that work filled, forcing it to regenerate the same state
   repeatedly, producing CPU spikes and out-of-memory kills.
5. Duties are missed network-wide.

Steps 3–5 are a consensus-client bug and are out of scope for a node-local tool.
**Step 1 is not.** It is the condition an operator is sitting in front of, and in
2023 they had no way to see it except by inference.

## What whymiss reports for step 1

`local.el_slow` (`docs/causes.md`): the execution client consumed the validation
budget, evidenced by Engine API call durations against a rolling baseline of that
node's own recent behaviour.

That is the product's central question applied to this incident. An operator
missing attestations during those hours had to decide whether their node was
broken or the network was. The public timeline took days to assemble.

## The reproduction

The mechanism is reproduced by `test/corpus/el-slow-cpu`, generated by
`tools/faultinjector` against a three-node Kurtosis devnet — Lighthouse and two
Prysm nodes, each with its own geth — not a simulation:

| | |
|---|---|
| Fault | cgroup v2 `cpu.max`, execution client capped to **8% of one core** |
| Target | `el-1-geth-lighthouse`, the watched attester's own execution client |
| Duration | 25s, covering the duty window |
| Load | `spamoor` sustaining ~300 transactions per block |
| Watched duty | attester, validator index 1, slot 2245 |

Two details matter for honesty. The load is there because Engine work is 3–5ms
per block on an empty chain and 361ms under transaction load — a CPU cap can only
starve work that exists, which is why every earlier attempt at this cause on an
idle devnet failed regardless of severity. And `avoid_proposer_validators` forces
the block to arrive over gossip, so the watched node must actually import and
validate it rather than having produced it itself.

The cap is a throttle, not a kill. The execution client stayed up and answering
throughout, which is the 2023 condition — *slow*, not *absent*.

## What whymiss said

Replaying the record through `rca.Analyze`, unedited:

```
# Slot 2245 — local.el_slow

**Outcome:** degraded (lost: timely_head)
**Confidence:** medium

## Evidence

- [+10.922217424s] execution client's 3 newPayload call(s) totaled 9928.92ms in the
  canonical-head window (newPayload duration: 9928.92 vs 0 ms) — *promscrape*
- [+10.922217424s] execution client's 1 forkchoiceUpdated call(s) totaled 41.86ms in
  the canonical-head window (forkchoiceUpdated duration: 41.86 vs 0 ms) — *promscrape*
- [+10.922217424s] Engine API calls totaled 9.970780157s against a 491.23ms rolling
  p99 and consumed at least half of validation (Engine API total vs spike threshold:
  9970.78 vs 1473.68 ms) — *derived*

## Remediation

1. check the execution client version against the latest release
2. inspect execution-client logs and host I/O telemetry for the exact canonical-head
   window before assigning a sub-cause
```

The numbers, all from the committed record:

- the block was seen at **+0.50s** — propagation was fine, so this was not the
  network;
- the head arrived at **+10.92s**, against a 4s attestation deadline;
- Engine calls totalled **9970.78ms** against this node's own **491.23ms** rolling
  p99 — **20.3x** its normal behaviour, and 6.8x the 3x spike threshold R-300
  requires before it will speak.

Confidence is `medium`, not `high`, and deliberately: the rule can say the
execution client consumed the budget, but not *why* it was slow. Naming a
sub-cause — pruning, snapshotting, disk saturation — needs evidence this timeline
does not carry, so the remediation asks for it instead of guessing. Under I-8 a
narrower true statement beats a wider plausible one.

## What this would have meant in May 2023

For an operator whose own execution client was struggling, whymiss would have
answered the question in one slot, with the Engine measurements attached: *your
execution client, not the network.* Not the Prysm cache bug, and not the
network-wide diagnosis — but the fact that determined what they should do, at the
moment they needed it.

And for an operator whose node was healthy while the network was not, the
opposite matters as much: `local.el_slow` requires positive Engine evidence, so a
node behaving normally does not get blamed. The rule declines and the verdict
falls to a `network.*` cause or an honest `unknown`.

## Verifying this yourself

```sh
make eval                       # scores every record; el-slow-cpu appears in docs/evaluation.md
cat test/corpus/el-slow-cpu/manifest.yaml   # the recipe, the fault, and the bisection reasoning
```

The record's observations and samples are content-hashed in its manifest, so the
numbers above cannot drift from the evidence without `make corpus.validate`
failing.
